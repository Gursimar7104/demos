Deployment audit of 3 Persona customers

Lime's help page still tells riders to scan an ID first, though Persona's case study says Lime's selfie-first flow lifted conversion from 80% to 93%

Built by Gursimar Singh, Nov 2026, on real public data

The role runs audits of live Persona deployments and turns them into recommendations. I walked 3 Persona customers' public verification docs up to the ID step: OpenAI, Coursera and Lime. Each one has a gap a config change could close, from OpenAI rejecting mobile driver's licenses to Coursera having no non-biometric path.

I did not create accounts or start any verification. Every step and friction point comes from the customer's own public help page or Persona's public case study and docs, quoted in the CSV. The recommendations are my suggestions, each tied to a Persona feature named in its public help center or product pages.

OpenAI: API organization verification

Flow up to the ID step (from public docs)

  • Entry: a verification prompt or notice inside the API platform ("Start from the verification prompt or follow the instructions in the notice you received." source)
  • Pre-ID: business details for business verification (legal name, address, tax ID if requested) ("Your organization’s legal name exactly as it appears in official records." source)
  • ID step: original physical government ID, selfie if requested ("You need an original, physical government-issued ID from one of our supported countries and territories, plus a device that can capture a cl..." source)

Friction

  • Digital IDs and mobile driver's licenses are rejected ("Photocopies, screenshots, scans, electronic replicas, mobile driver’s licenses, or digital ID cards." source)
  • A failed check is a dead end with no reason given ("Verification results cannot be manually overridden, and additional details about a specific decision are not available." source)
  • One person can verify only one org, which blocks consultants and agencies ("For identity verification, individuals can verify only one account or organization." source)

3 config recommendations

  1. Turn on mDL / digital ID as an accepted method for developers who carry a wallet ID ("Setting up Samsung Wallet and Google Wallet mDL verification" source)
  2. Add fallback ID types so a rejected first document can be retried with a second one in the same inquiry ("Setting accepted fallback ID types for Government ID Verification" source)
  3. Send borderline fails to manual review in case management instead of a hard decline, and return a reason code the help article can map to ("Manual review" source)

Coursera: ID verification for certificates

Flow up to the ID step (from public docs)

  • Entry: Settings page, ID Verification section ("Scroll down to the ID Verification section (you’ll only see this section if you’re enrolled in a class that requires it)." source)
  • Pre-ID: name, birthdate and ID country ("Your first and last name, birthdate, and the country your ID is from" source)
  • ID step: photo of ID, then selfie (ID must pass first) ("Your government ID must be verified before you can upload a selfie." source)

Friction

  • No non-biometric path at all ("Coursera is unable at this time to offer alternative verification methods." source)
  • Outside the listed countries, passport is the only common ID ("Additional Countries / / Passport" source)
  • Help doc tells learners to switch to a computer or browser, a sign mobile capture fails ("Try using a computer instead of a mobile device." source)

3 config recommendations

  1. Prefill name and birthdate from the ID and compare, instead of typing them before the ID step ("Configuring the Inquiry Comparison Check for Government ID Verification" source)
  2. Offer database verification as the non-biometric fallback in countries where it is supported ("Setting match requirements for Database Verification (Non-US & International)" source)
  3. Add per-country fallback ID types so learners outside the listed countries are not limited to passports ("Setting accepted fallback ID types for Government ID Verification" source)

Lime: Rider age verification

Flow up to the ID step (from public docs)

  • Entry: prompt before a ride in cities that require age checks ("In some cities, you must verify your age before you can ride Lime vehicles." source)
  • ID step: scan a government ID before the ride, or enter info manually ("If you need to verify your age, you’ll get prompted to scan your government-issued identification document before your ride." source)

Friction

  • The help page, last updated April 25, 2024, still describes an ID-scan-first flow ("you’ll get prompted to scan your government-issued identification document before your ride." source)
  • Persona's case study says Lime moved to selfie first, with ID only if the selfie suggests underage ("it recently launched a verification flow that only requires riders to scan their ID if their selfie suggests that they’re underage." source)
  • Help page shows 281 of 448 riders found it helpful, so about 37% did not ("281 out of 448 found this helpful" source)

3 config recommendations

  1. Update the help page to match the selfie-first flow so riders know an ID may not be needed ("Step-up verification" source)
  2. Tune age thresholds and buffers per city so fewer riders near the cutoff get stepped up to an ID scan ("Configurable age thresholds and buffers" source)
  3. Route borderline selfies to the fallback method automatically and redact data after ("route borderline users to fallback methods" source)

How it works

  • Pick 3 customers from Persona's public customer page that also publish a help article on their own verification flow.
  • Log each flow from entry point to the ID step, plus friction, using only quotes from those public pages.
  • Match each friction point to a Persona feature documented in its help center (fallback ID types, mDL, database verification, age thresholds, manual review) and write 3 recommendations per customer.

What I'd improve next: Get permission to run test inquiries in each flow and time every step on mobile and desktop, then pull real drop-off by step from the Persona dashboard to rank which fix moves conversion most.
